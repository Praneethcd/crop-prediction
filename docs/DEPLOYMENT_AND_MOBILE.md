# Deployment and mobile distribution

The Flask project has a production Dockerfile, persistent storage configuration, health endpoint, background monitor, Render blueprint and Android/iOS app sources. **These files do not mean the service has already been deployed.** Actual hosting and signed mobile distribution require the chosen provider/account, a public HTTPS URL and platform signing. The code and workflows are now published to the existing GitHub repository.

## Backend deployment

`Dockerfile` uses Python 3.11 and CPU PyTorch. It excludes `.env`, local databases, uploaded images, Git history and notebook data from the build. The disk `/data` holds SQLite and private image uploads so restarts preserve farmer records. Gunicorn runs one worker with four threads; a separate process checks holdings every 15 minutes. Deploy a single instance for this SQLite design; move to PostgreSQL/object storage before horizontal scaling.

Use `compose.yaml` for your own server:

```sh
cp .env.example .env
# Set SECRET_KEY to a long random private value, then set the market key if available.
docker compose up --build -d
```

Terminate HTTPS at your hosting provider or reverse proxy. The native clients require a valid HTTPS URL. Local Docker requires an active Docker daemon, which was not running on the development machine during verification, so container verification ran on GitHub Actions instead. The production image builds and its health check passes.

`render.yaml` is a blueprint for a paid web service with a persistent disk. Its selected plan is a configuration proposal, not a purchase or a deployed resource. Review current provider costs before creating it. Free ephemeral hosting is not suitable for this SQLite/upload design. Optionally enter AGMARKNET_API_KEY and ADMIN_EMAIL/ADMIN_PASSWORD in Render's private environment settings; SECRET_KEY is generated by the blueprint. Production does not create the original `admin123` default admin. If no admin credentials are supplied, register a farmer account to use the product.

The public repo is `https://github.com/Praneethcd/crop-prediction`. The implementation and build workflows have been pushed to main; repository-based deployment can now use them. Do not publish `.env`, signing keys or local user database/uploads. Existing tracked files need a privacy review before exposing any previously private repository; this repository is already public.

Check `/healthz`, sign-in, leaf inference, forecast, persistent storage across restart, and the monitor status before distributing an app. The backend performs ML inference; native apps require network access rather than bundling models on the device.

## Android APK

`mobile/android` contains a native Java WebView app that loads the **real deployed site**, with an HTTPS host allowlist, blocked invalid certificates/mixed content, browser navigation for outside HTTPS links and a file/camera picker for leaf photos. It does not add a JavaScript-native bridge to remote content.

The build intentionally fails without a deployment URL:

```sh
cd mobile/android
gradle -PappUrl=https://YOUR-REAL-SITE assembleDebug
```

Use JDK 21, Gradle 8.13, Android SDK platform 36 and build tools compatible with Android Gradle Plugin 8.13.2. No Android SDK was installed locally during preparation; Android compilation has passed on GitHub Actions. `.github/workflows/android.yml` supplies a manual GitHub Actions build with those tools. After pushing the changes, run **Build Android APK** with the deployed URL and download the `AgriPredict-Android-testing-APK` artifact. The debug APK is installable for testing; it is not a Play Store release. A signed release APK/AAB requires your maintained signing key and release policy. Do not distribute an APK pointing at `localhost`, an example domain or a temporary test database.

## iPhone / iOS

iOS cannot run an Android APK. `mobile/ios/AgriPredict.xcodeproj` is a native SwiftUI + WKWebView client for the same HTTPS backend. Its camera/photo purpose strings are included and it limits navigation to the configured host.

Open the project in Xcode, set `AGRIPREDICT_URL` to the deployed HTTPS origin, select your Apple team, and archive for TestFlight/App Store using your own signing credentials. The bundle ID defaults to `com.agripredict.app`; choose an identifier you control before release. An unsigned iOS simulator build has passed on GitHub Actions; no signed iPhone build has been produced. Locally, local `xcodebuild` stopped because **the Xcode/Apple SDK license has not been accepted on this Mac**. The user must review and accept that agreement; it was not accepted automatically.

Apple Developer enrollment, signing/provisioning, App Store Connect access, required privacy disclosures and review are separate external steps. A source project or unsigned simulator build is not an installable IPA. No TestFlight/App Store upload has occurred. Add production app icons/screenshots and validate camera upload, login, back navigation and reconnect behavior on real devices before release.

## Installable web app on both platforms

The project includes a manifest, service worker and app icon. Once deployed over HTTPS, Android browsers can offer installation and iPhone Safari can add the site to the Home Screen. This is a PWA, separate from an Android APK or iOS IPA. The offline screen clearly explains that analysis and market decisions require internet. Private dashboards, APIs, farmer photos and disease results are never cached by the service worker.

## What is still required externally

- Choose a hosting account/provider and provide access through that provider's normal secure flow.
- Configure the data.gov.in API key for live market quotes; initialize history via CSV/import if the current-price cache has fewer than 14 observations.
- Deploy and verify a stable HTTPS URL; compile the apps against that actual URL.
- For Android release distribution, provide/use your signing keystore and choose APK or Play Store AAB.
- For iPhone distribution, accept the local Xcode agreement and configure the Apple Developer team and TestFlight/App Store destination.

Reference documentation: [Render Flask hosting](https://render.com/docs/deploy-flask), [persistent disks](https://render.com/docs/disks), [Android build documentation](https://developer.android.com/build), [Apple app distribution](https://developer.apple.com/help/app-store-connect/manage-builds/upload-builds/).

Verification evidence: [successful backend, Android, iOS simulator and Docker checks](https://github.com/Praneethcd/crop-prediction/actions/runs/37004013007). The native compile checks use a placeholder origin and do not distribute installable apps. The APK distribution workflow must be run again with the actual deployed URL.

### No-key pricing and measured performance
The Render blueprint now requires only its generated session secret; a government API key is optional. Farmers can upload UTF-8 CSV to `/market-history/import` with `lot_id`, `file`, `price_unit` (quintal/tonne/kg), and a `source_label`. Simple `date,price` and mandi `Arrival_Date,Modal_Price` exports are supported. Present commodity/location/variety/grade columns must match the lot; ambiguous locations and conflicting daily quotes are rejected. Uploaded prices are farmer supplied, not independently verified by the app.

`POST /market-validation` with `lot_id` evaluates Prophet against a withheld final calendar week of saved prices (at least 28 observations). It reports MAE, RMSE, MAPE and an unchanged-price baseline; no held-out observations enter training. This is a single holdout, not a claim of guaranteed future accuracy. CSV prices must be kept current manually when no live-feed key is configured.
